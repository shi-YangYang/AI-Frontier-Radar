# Rework

## 背景

本地启动实测：6 个 YouTube handle 解析全部失败（代理瞬时故障），seed 在建包前中断，4 个新内置包一个都没创建；且已存在的内置包不会在后续启动补挂缺失成员。本轮返工修两个缺陷。

## 缺陷与修复

1. 单条源失败中断整个种子 → 每条源独立 try/catch（X/RSS 源创建、YouTube 解析均隔离），失败记 warn + skippedSources 后继续；建包只引用 ensure 成功的成员，缺失成员跳过（warn 含包名与源标识），包仍创建（允许部分成员）。`seedSourcePacks` 顶层 try/catch 兜底：异常只记日志不抛出，服务启动不被种子失败拖垮，缺失内容下次启动重试。
2. 已存在内置包缺种子成员无法补挂 → 每个启动周期对已存在的内置主题包补挂缺失的种子成员（先逐条 ensure 源，成功后与包现有成员差集补挂，幂等）。YouTube 解析失败后，下次启动解析成功即经同一补挂路径自动挂入。

## 语义权衡（有意变更）

「种子不覆盖管理员的修改」调整为：**内置主题包跟随种子收敛到完整成员**——管理员从内置包删除的种子成员，会在下次启动被重新补挂（包属性与非种子成员不受影响）。理由：种子成员代表产品维护的基线内容集，跨启动收敛保证网络瞬时故障（如 YouTube 解析失败）留下的缺口能自动补齐。

边界：

- 管理员的非内置包（自建包）完全不受种子影响；
- 内置包的名称/描述/启停/排序不被种子覆盖；
- 论文包（存量「AI 消息」改名）保持原改名语义：保留 id / 已有成员 / 描述，种子不补挂论文包成员（存量改名测试明确断言成员保留）。

## 验证

- smoke 新增：YouTube 全失败场景下 4 个内置包仍按部分成员创建（6 个 handle 记入 skippedSources）；下一次 seed（模拟解析成功）6 个源补建并自动补挂进 3 个已存在内置包；再跑一次 seed 全量幂等（无新建/无补挂/无跳过）。
- `npm run typecheck`、`npm run smoke:e2e`、`npm run build` 通过。
- spec.md 汇总行计数修正为 X×18、YouTube×6、RSS×5（共 29）。
