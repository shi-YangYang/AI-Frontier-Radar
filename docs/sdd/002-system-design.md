## 1. 文档目标

定义 V1 的系统拆分、模块职责、关键数据流、运行方式和实施边界，作为后续实施 Agent 编码的直接依据。

## 2. 设计输入

本设计基于以下前提：

- V1 使用 X `User Timeline Polling`
- V1 使用飞书群自定义机器人 webhook
- V1 不在飞书内管理监测账号
- V1 目标是准实时、低成本、稳定去重
- 项目采用“协调 Agent + 实施 Agent”协作模式

## 3. 系统目标

V1 系统需要满足：

- 周期性拉取指定 X 账号的最新帖子
- 识别新帖并可靠去重
- 将新帖异步推送到飞书
- 在失败或重启后保持状态一致
- 为 V2 升级到飞书应用机器人和更复杂数据源预留接口

## 4. 总体架构

V1 建议拆为 5 个逻辑模块：

1. `config`
2. `api`
3. `polling-worker`
4. `delivery-worker`
5. `storage`

其中：

- `config` 负责加载与校验配置
- `api` 负责本地管理接口和健康检查
- `polling-worker` 负责拉取 X 时间线并生成事件
- `delivery-worker` 负责发送飞书并处理重试
- `storage` 负责数据库与队列状态持久化

## 5. 模块设计

## 5.1 config

职责：

- 读取环境变量
- 读取本地配置文件
- 校验配置合法性
- 生成统一配置对象

配置范围至少包括：

- 数据库连接
- Redis 连接
- 飞书 webhook
- 默认轮询间隔
- 单次拉取数量
- 是否排除回复
- 是否排除转推
- 监测账号列表

设计要求：

- 配置不能散落在业务代码中
- 所有配置必须有单一入口
- 配置结构应支持未来从文件切换到本地 Web 管理

## 5.2 api

V1 的 `api` 是轻量内部接口，不是公网产品接口。

职责：

- 提供健康检查
- 提供配置查看能力
- 如果进入 V1.1，可提供本地 Web 管理接口

V1 最小要求：

- `/health`
- `/ready`

可选预留：

- `/watch-accounts`
- `/metrics`

## 5.3 polling-worker

这是 V1 的核心模块。

职责：

- 读取启用中的监测账号
- 按调度规则轮询 X 时间线
- 过滤非目标帖子
- 识别新帖
- 保存原始帖子
- 生成待投递任务
- 更新轮询状态

内部建议再抽象两层：

- `SourceProvider`
- `PollingOrchestrator`

`SourceProvider` 负责与 X 交互。

`PollingOrchestrator` 负责轮询顺序、状态推进和事件生成。

这样后续如果切换到其他数据源，不需要重写整体流程。

## 5.4 delivery-worker

职责：

- 消费待投递事件
- 格式化飞书消息
- 调用飞书 webhook 发送
- 记录成功与失败状态
- 触发重试与退避

设计要求：

- 投递必须受幂等控制
- 重试不能绕过去重逻辑
- 发送失败不能反向影响主轮询链路

## 5.5 storage

V1 使用：

- SQLite 保存业务状态
- Redis + BullMQ 保存任务队列状态

SQLite 保存：

- 监测账号
- 轮询状态
- 原始帖子
- 投递记录
- 运行日志索引

Redis + BullMQ 负责：

- 待投递任务
- 延迟重试任务
- 并发消费控制

## 6. 关键数据流

## 6.1 轮询流程

1. 调度器触发轮询
2. `polling-worker` 读取启用中的账号
3. 对每个账号调用 `SourceProvider`
4. 返回最新帖子列表
5. 过滤回复、转推等非目标帖子
6. 基于轮询状态与数据库判断哪些是新帖
7. 写入原始帖子表
8. 为每条新帖创建投递事件
9. 推进该账号的轮询状态

## 6.2 投递流程

1. `delivery-worker` 从队列取任务
2. 根据帖子内容生成飞书消息体
3. 检查幂等记录
4. 调用飞书 webhook 发送
5. 记录发送结果
6. 失败时根据策略重试

## 7. 状态管理设计

## 7.1 账号状态

每个监测账号至少需要保存：

- 唯一标识
- X 用户名
- X 用户 ID
- 是否启用
- 最近成功轮询时间
- 最近处理的最大帖子 ID
- 首次接入基线帖子 ID

## 7.2 首次接入基线

首次接入某账号时，不推送历史消息。

实现方式：

- 首次拉取到的最新帖子 ID 记录为 `baseline_post_id`
- 只有后续大于该基线的新帖子才允许进入投递流程

## 7.3 幂等状态

幂等键使用：

- `x_post_id + feishu_target_key`

只有当该组合不存在成功记录时，才允许实际发送。

## 7.4 失败状态

对于发送失败的任务，需要保存：

- 失败次数
- 最近失败原因
- 下次重试时间
- 最终状态

## 8. 调度设计

V1 建议采用固定间隔轮询。

设计原则：

- 简单优先
- 成本可控
- 行为可预测

调度模型建议：

- 全局定时器触发一轮扫描
- 单轮内按账号逐个或受限并发执行
- 并发度必须可配置

V1 暂不引入过度复杂的分布式调度。

## 9. 失败处理设计

## 9.1 X 拉取失败

如果某次拉取失败：

- 记录错误日志
- 不推进该账号的最新处理位置
- 下一轮继续尝试

## 9.2 飞书发送失败

如果飞书发送失败：

- 标记投递失败
- 按重试策略重投
- 重试前再次检查幂等状态

## 9.3 服务重启

服务重启后：

- 轮询状态从数据库恢复
- 待发送任务从队列和数据库恢复
- 不允许因重启导致旧消息重复大规模补发

## 10. 本地运行与部署形态

V1 支持两种运行形态：

### 10.1 单进程开发模式

适用于本地开发与调试：

- 一个应用进程内同时启动 `api`、`polling-worker`、`delivery-worker`

### 10.2 分角色部署模式

适用于正式运行：

- `api` 独立进程
- `polling-worker` 独立进程
- `delivery-worker` 独立进程

这样可以避免不同职责互相影响，并便于后续扩展。

数据库迁移策略：

- V1 默认使用 SQLite
- 未来如出现更高并发或多实例部署需求，再迁移到 MySQL
- 实现时避免依赖 SQLite 专属写法，尽量为后续迁移保留空间

## 11. 扩展点设计

V1 应显式预留以下扩展点：

- `SourceProvider`：未来切换到流式或其他数据源
- `DeliveryChannel`：未来支持飞书应用机器人
- `AccountRepository`：未来从配置文件切换到本地 Web 管理或数据库管理
- `MessageFormatter`：未来支持摘要、卡片、分类

## 12. 协调 Agent 与实施 Agent 边界

## 12.1 协调 Agent 负责

- 确认上位约束
- 维护 specs
- 决定模块边界
- 决定接口契约
- 拆分工作包
- 做实现验收

## 12.2 实施 Agent 负责

- 按当前 specs 完成模块实现
- 在不突破规格边界的前提下细化局部实现
- 提交实现说明与风险点

## 12.3 禁止事项

实施 Agent 不应：

- 自行修改产品范围
- 自行替换核心技术路线
- 在未沟通的情况下把轮询方案改为其他抓取方式
- 绕过幂等与状态设计做一次性脚本式实现
