## 1. 文档目标

将 V1 的实施工作拆为可分配、可验收、可并行度控制的里程碑和工作包，供协调 Agent 后续拆给实施 Agent。

## 2. 推进原则

- 先打底座，再接外部依赖
- 先状态持久化，再跑业务链路
- 先单通路跑通，再做硬化
- 每个里程碑都必须有明确完成标准

## 3. 里程碑总览

V1 建议拆成 6 个里程碑：

1. M1 项目骨架
2. M2 配置与数据层
3. M3 轮询链路
4. M4 投递链路
5. M5 API 与运行观察
6. M6 联调与验收

## 4. 里程碑明细

## 4.1 M1 项目骨架

目标：

- 建立 TypeScript + Fastify + Prisma 基础工程
- 建立基本目录结构
- 建立配置加载入口

建议产出：

- 项目初始化
- 基本脚本命令
- 环境变量模板
- 日志基础设施

完成标准：

- 项目可启动
- 配置可加载
- 健康检查路由可运行

适合实施 Agent 的工作包：

- `M1-A`: 工程初始化与脚本配置
- `M1-B`: 基础日志与配置模块

## 4.2 M2 配置与数据层

目标：

- 完成 SQLite 数据模型
- 完成 Prisma schema
- 完成数据库初始化和迁移流程

建议产出：

- `watch_accounts`
- `x_posts_raw`
- `delivery_targets`
- `delivery_events`
- `poll_runs`

完成标准：

- 数据库可初始化
- 唯一约束和索引存在
- 能写入默认 `delivery_target`

适合实施 Agent 的工作包：

- `M2-A`: Prisma schema 与迁移
- `M2-B`: repository / storage 封装

## 4.3 M3 轮询链路

目标：

- 实现 `SourceProvider`
- 实现 `PollingOrchestrator`
- 完成首次接入基线逻辑
- 完成新帖识别和入库

建议产出：

- X 时间线拉取封装
- 帖子过滤逻辑
- `poll_runs` 记录
- `delivery_events` 创建

完成标准：

- 能拉取指定账号最新帖子
- 首次接入不补发历史消息
- 新帖只会创建一次投递事件

适合实施 Agent 的工作包：

- `M3-A`: X client 与标准化数据转换
- `M3-B`: 轮询编排与状态推进

## 4.4 M4 投递链路

目标：

- 实现飞书 webhook 发送
- 实现消息格式化
- 实现幂等控制和重试

建议产出：

- delivery worker
- retry 策略
- 发送结果持久化

完成标准：

- 新帖可发送到飞书
- 重复任务不会重复发送
- 失败任务可重试并落状态

适合实施 Agent 的工作包：

- `M4-A`: 飞书消息格式化与 webhook client
- `M4-B`: delivery worker 与 retry 机制

## 4.5 M5 API 与运行观察

目标：

- 实现必要 API
- 实现运行摘要和状态查看

建议产出：

- `/health`
- `/ready`
- `/config/summary`

可选：

- `/watch-accounts`
- `/poll-runs`
- `/delivery-events`

完成标准：

- 本地可通过 API 观察运行状态
- 依赖异常时 `/ready` 能正确失败

适合实施 Agent 的工作包：

- `M5-A`: 必做 API
- `M5-B`: 预留 API 或诊断接口

## 4.6 M6 联调与验收

目标：

- 串通完整链路
- 验证核心业务约束
- 补齐最小测试与运行说明

验收标准：

- 新帖出现后可进入飞书
- 首次接入不补发历史消息
- 重启后不会大规模重复推送
- 飞书失败会进入重试
- 运行日志能解释关键状态

适合实施 Agent 的工作包：

- `M6-A`: 集成测试与手工验证脚本
- `M6-B`: 运行文档与问题清单

## 5. 推荐执行顺序

推荐顺序：

1. `M1`
2. `M2`
3. `M3`
4. `M4`
5. `M5`
6. `M6`

原因：

- `M2` 是 `M3` 和 `M4` 的基础
- `M3` 跑通后，`M4` 才有真实输入
- `M5` 应建立在核心链路已成形的前提上

## 6. 可并行边界

在不冲突的情况下，可做如下并行：

- `M1-A` 与 `M1-B`
- `M2-A` 与 `M2-B`
- `M4-A` 与 `M5-A`

不建议并行的部分：

- `M3-B` 依赖 `M2`
- `M4-B` 依赖 `M4-A` 和 `M3`
- `M6` 依赖前面全部完成

## 7. 协调 Agent 的里程碑职责

协调 Agent 在每个里程碑负责：

- 确认输入文档是否充分
- 拆分工作包
- 明确每个实施 Agent 的边界
- 评审实施结果
- 判断是否进入下一里程碑

## 8. 实施 Agent 的交付要求

每个工作包交付时应至少包含：

- 实现了什么
- 改了哪些模块
- 如何验证
- 遗留风险
- 是否有超出 spec 的地方

## 9. 里程碑完成定义

一个里程碑只有在以下条件都满足时才算完成：

- 对应 spec 已覆盖
- 关键路径已实际跑通
- 有基本验证结果
- 没有明显违背上游约束

## 10. V1 完成定义

V1 只有在以下条件同时满足时才可认为完成：

- 能稳定轮询指定 X 账号
- 能将新帖发到飞书
- 不会明显重复发送
- 重启后状态可恢复
- 配置修改后可在下一轮生效

## 11. 下一步使用方式

后续由协调 Agent 基于本文件，把每个里程碑继续拆为更小的实施任务，再交给实施 Agent 执行。
