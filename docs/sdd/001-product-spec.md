## 1. 文档目的

定义 V1 版本的产品边界、目标用户、关键流程、成功标准和明确不做的内容。

本文件用于约束后续系统设计、数据模型和接口设计，避免开发过程中范围漂移。

## 2. 版本定位

V1 是一个“准实时监测 + 飞书消息通知”的最小可用版本。

V1 不追求：

- 严格实时
- 飞书内交互式管理
- 智能分析
- 多租户能力

V1 追求：

- 稳定抓取
- 不重复推送
- 配置简单
- 易于后续演进到 V2

## 3. 用户与场景

## 3.1 目标用户

当前阶段的唯一用户是你自己或你的内部小团队。

你们的目标不是开放给公众使用，而是先把“AI 博主监测 -> 飞书触达”这条链路跑通，并验证是否值得继续做大。

## 3.2 核心使用场景

用户希望持续关注若干 AI 消息博主的 X 发帖，并在新帖出现后尽快在飞书收到通知。

典型场景：

- 关注 AI 行业新闻账号
- 关注产品发布、模型更新、融资、组织变动等消息
- 避免手动频繁刷 X

## 4. V1 功能范围

## 4.1 必做功能

### 4.1.1 监测指定 X 账号的新帖

系统需要能够周期性查询指定 X 账号的最新帖子，并识别相对上次检查之后的新帖子。

### 4.1.2 支持配置监测账号列表

V1 的账号列表通过以下两种方式之一管理：

- 本地配置文件写死
- 本地 Web 应用管理

V1 不要求飞书内动态管理。

### 4.1.3 新帖去重

同一条 X 帖子对于同一飞书目标只能推送一次。

即使发生以下情况，也不能重复推送：

- 轮询重复扫到同一帖子
- 服务重启
- 飞书投递重试

### 4.1.4 推送到飞书

发现新帖后，系统需要将帖子内容格式化并推送到飞书目标群。

V1 默认采用飞书群自定义机器人 webhook。

### 4.1.5 投递与运行日志

系统需要记录：

- 每次轮询的执行情况
- 发现了哪些新帖
- 哪些消息投递成功
- 哪些消息投递失败
- 失败原因

### 4.1.6 基础启停能力

V1 至少需要支持对单个监测账号做启用/停用。

如果 V1 采用纯配置文件方案，那么启停通过修改配置并重载实现。

如果 V1 采用本地 Web 应用方案，那么启停通过页面操作实现。

## 4.2 可选功能

以下能力可以作为 V1.1 或 V1.2，不强制进入首版：

- 本地 Web 管理页
- 帖子链接预览优化
- 按账号单独配置推送目标
- 轮询频率配置化
- 失败告警

## 4.3 明确不做

V1 不做以下能力：

- 飞书内添加 / 删除监测账号
- 飞书卡片交互管理
- LLM 摘要
- 自动打标签
- 热度评分
- 情绪分析
- 多租户与权限系统
- 面向公网的用户系统
- 移动端 App

## 5. 业务规则

## 5.1 监测对象

监测对象是 X 上的公开账号。

V1 仅监测账号“发出的帖子”，不监测：

- 点赞
- 关注关系变化
- 转推行为以外的其他动态

关于“帖子”的 V1 默认范围，建议如下：

- 包含原创帖子
- 默认排除回复
- 默认排除转推

这样可以减少噪音，更贴近“AI 前沿消息”目标。

这个规则后续可配置化，但 V1 先固定。

## 5.2 新帖判定

如果某账号最新拉取到的帖子 ID 大于该账号已处理的最大帖子 ID，并且数据库中不存在对应投递记录，则视为新帖。

## 5.3 去重规则

幂等键建议定义为：

- `x_post_id + feishu_target_key`

只要这个组合已经成功投递过，就不允许再次推送。

## 5.4 推送内容

V1 推送内容建议至少包含：

- 发帖账号名
- 发帖时间
- 帖子正文
- 原帖链接

如果帖子正文过长，可在飞书消息中截断，但原帖链接必须保留。

## 6. 非功能要求

## 6.1 稳定性

系统重启后不能因为状态丢失而重复发送大量历史消息。

## 6.2 可观测性

至少需要有文本日志，能回答以下问题：

- 某次轮询是否成功
- 某个账号最近是否抓到新帖
- 某条帖子为什么没有发到飞书

## 6.3 可维护性

账号列表、轮询频率、飞书 webhook、过滤选项等配置必须集中管理，不能散落在代码里。

## 6.4 成本控制

由于当前不接受 X 付费 API 实时流，V1 必须以“尽量低成本的轮询方案”为前提设计。

## 7. 关键流程

## 7.1 正常流程

1. 定时任务触发轮询
2. 系统读取启用中的监测账号列表
3. 逐个查询每个账号最新帖子
4. 过滤非目标帖子
5. 与历史记录比对，识别新帖
6. 将新帖原始数据入库
7. 生成待投递事件
8. 推送飞书
9. 记录投递结果
10. 更新该账号的最新处理位置

## 7.2 失败流程

如果 X 请求失败：

- 记录失败日志
- 不推进该账号的最新处理位置
- 等待下一轮继续拉取

如果飞书发送失败：

- 记录失败日志
- 保留待重试状态
- 重试时仍需受幂等控制

## 7.3 首次启动流程

首次启动时需要避免把目标账号的大量历史帖子全部推送到飞书。

V1 默认规则建议为：

- 首次接入账号时，将当前最新帖子 ID 记为起点
- 仅监测接入之后产生的新帖

这条规则很重要，后续实现必须显式支持。

## 8. 成功标准

V1 上线后，以下条件满足即可视为成功：

- 能稳定监测一组指定 AI 账号
- 新帖能在可接受时间内推送到飞书
- 没有明显重复推送
- 服务重启后不会大量补发旧消息
- 账号配置改动后可在下一轮生效

## 9. 当前冻结的产品决策

截至 2026-04-21，V1 冻结如下：

- X 数据获取方式：轮询 `User Timeline`
- 实时性：准实时
- 飞书接入：群自定义机器人 webhook
- 配置方式：脚本写死或本地 Web 应用
- 飞书内管理：不做
- V2 再考虑飞书交互式管理

## 10. 待后续规格明确的事项

以下问题留到后续设计文档细化：

- 轮询频率的默认值
- 单次拉取每个账号取多少条帖子
- 本地 Web 管理页是否进入 V1
- 失败重试策略
- 数据库表结构
- 本地部署还是服务器部署
