# Tech Stack

## 目标

本文件定义当前阶段的默认技术路线和约束。除非后续有明确决策变更，否则后续设计和实现应以本文件为准。

## 已确认约束

截至 2026-04-21，当前已确认：

- 不接受使用 X 官方付费 API / credits
- V1 不在飞书内管理监测账号
- V1 的监测账号先通过脚本写死或本地 Web 应用管理
- V2 再升级为飞书内直接管理

## V1 默认技术路线

- 语言：TypeScript
- 运行时：Node.js
- 后端框架：Fastify
- 数据库：SQLite
- 队列：Redis + BullMQ
- ORM：Prisma
- X 数据源：User Timeline Polling
- 飞书接入：群自定义机器人 webhook

## 选型理由

### TypeScript / Node.js

项目包含：

- 周期轮询
- Web API
- 异步任务
- JSON-heavy 的第三方接口交互

这类场景适合 Node.js + TypeScript，原因是：

- I/O 密集型任务处理顺手
- 类型约束适合管理 X 和飞书接口数据
- 后续如果补本地 Web 管理端，前后端可统一语言

### Fastify

选择 Fastify 的原因：

- 足够轻量
- 启动快
- 适合内部 API 和 webhook 接口
- 与 TypeScript 配合较顺

### SQLite

项目需要清晰保存：

- 监测账号
- 原始帖子
- 轮询状态
- 投递记录
- 幂等键

V1 这些数据量很小，且当前目标是单机、低成本、快速验证链路，SQLite 更合适，原因是：

- 部署最轻
- 本地开发最简单
- 不需要额外数据库服务
- 足以支撑 V1 的状态持久化与去重需求

后续如果出现以下信号，再迁移到 MySQL：

- 多实例部署
- 更高并发写入
- 更复杂的管理后台
- 更大规模的历史数据和分析结果

### Redis + BullMQ

监测与投递需要解耦：

- 轮询发现新帖
- 生成投递任务
- 失败重试
- 控制并发与退避

BullMQ 适合承担这类后台任务模型。

### Prisma

选择 Prisma 的原因：

- 与 TypeScript 协作自然
- 数据模型表达清晰
- 迁移管理成本较低

## X 接入策略

V1 固定使用 `User Timeline Polling`，不使用付费实时流。

理由：

- 符合当前成本约束
- 适合先验证业务价值
- 实现复杂度显著低于流式长连接

设计要求：

- 从第一天就抽象 `SourceProvider`
- 后续允许升级到 Filtered Stream 或其他数据源

## 飞书接入策略

V1 固定使用飞书群自定义机器人 webhook。

理由：

- 足够支撑单向通知场景
- 实现最轻
- 适合当前“不在飞书里管理”的边界

V2 再考虑升级到飞书应用机器人，用于：

- 交互式管理
- 事件回调
- 卡片交互

## 部署建议

由于目标数据源是 X，部署建议优先选择：

- 香港
- 新加坡
- 东京

原则：

- 保证访问 X 的稳定性
- 保持部署成本可控

## 配置原则

以下配置必须集中管理，不允许写死在业务代码中：

- 监测账号列表
- 飞书 webhook
- 轮询间隔
- 单次拉取数量
- 是否排除回复
- 是否排除转推

## 后续可调整项

以下内容允许在后续规格中细化，但不能违背本文件的上位约束：

- 本地 Web 管理页是否进入 V1
- 轮询调度实现细节
- 重试与退避策略
- 日志与监控方案
- MySQL 迁移时机与迁移方案
